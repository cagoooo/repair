# RDQ 需求規格：報修系統下一階段優化

## 一句話任務
依據 v0.12.0 已完成的換版安全基礎，選定下一批最值得開發的 P0／P1 功能。

## 已確認
- v0.12.0 已完成換版精靈、發布阻擋、OCR 疑慮佇列、動態管理員安全上傳與 Firebase 規則回歸測試。
- 目前正式資料基準為 **101 間教室、48 筆歷史報修、0 筆失聯**。
- P0-3 必須等真正的 **115 學年度配置圖**才能完成實圖演練。
- 使用者要先查看完整候選清單，再自行決定後續開發內容。

## 待確認假設
- 下一階段仍以「不影響現有報修與共用 Firebase 專案」為最高限制。
- 功能可分批開發，每批完成後都需測試、更新進度表並部署。
- 未被選中的項目只代表本次不納入，不代表永久取消。

## 已採納建議
- 尚待使用者從 A–E 開發組合或個別 P0／P1 編號中選擇。

## 一段式需求規格
在不改動現有正式教室配置與歷史報修資料的前提下，依使用者選定的 P0／P1 編號開發下一階段功能；每項必須具備明確問題、範圍、依賴、風險及可觀察驗收證據，任何涉及 Firebase schema、規則、Functions 或 Storage 的變更均須通過共用專案回歸測試，並維持 **companion** 獨立資料庫不在部署範圍內。

## 驗收條件
- [ ] 使用者明確選定一個開發組合或個別功能編號。
- [ ] 選定項目已轉成可執行的分階段計畫與驗收案例。
- [ ] 未選項目保留在進度表，不被誤標為完成或取消。
